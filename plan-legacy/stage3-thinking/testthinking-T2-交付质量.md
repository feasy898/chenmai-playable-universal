# T2 交付质量测试 · 思考轨迹（stage3）

> 视角：DoD 每一级（L0 构建→L3 吸引人）逐级怎么测。作者 GLM 5.3 Flash（T2），2026-10-03。
> 测试对象：`最终规划文档.md` §2（DoD）、§4（合规矩阵）、§6（oracle 比对与吸引力）。仓内证据：qacore checks.ts/run.ts/autoplay.ts/mutations.mjs、engine-bridge events.ts、channel-rules.json 1.1.0。

## 一、先定总骨架：一次采集、多级判定、级间 blocked 语义

读完规划 §2 我的第一反应是：L0–L2 不该是四个判官跑四遍，而是**同一条 facts 采集管线上的不同判定切片**。现仓 qacore 已经是「run.ts 采集 / checks.ts 判定」的采集-判定分离结构，这是最值钱的既有资产——升级线应该顺着它长：探针族扩容一次，CHK 判定按级分组，每级判定是 facts 的一个谓词集合。

这样做直接兑现规划的三铁纪律里的「条件式裁定」：L0 谓词先算，L0 不过时 L1/L2 的判定输出不是 fail 而是 **blocked（未达判定前提）**。这区分「没测到」和「测了不过」，是失败分类学 F3/F4/F5 能落位的前提。skip≠pass 纪律同理延伸到级粒度：每级记录该级判据的 skip 占比，>10% 整级不采信（规划 §2 已写，测试实现上就是报告 JSON 加 `levels:{L0:{status,skip_ratio},…}` 字段）。

退出码语义不动：qacore 单次运行仍是 0/1/2（任何 CHK fail→1），分级结果只进报告、由上层批跑器聚合成 §2.3 的条件通过率 P(L1|L0)。这是与现仓 eval 文化（退出码语义是复用项，规划 §5.3）咬合的最小摩擦方式。

**前置门，必须写在最前面**：基线§六.3 证实环境即门槛（node_modules/playwright 全无，qacore.test.mjs 5/5 fail）。T2 的一切设计在该环境跑绿之前都是纸面推演。所以 L0 测试清单的第一条不是任何 CHK，而是「环境重建 + 现有 5 用例跑绿」本身作为 M0 门——规划 M0 出口已列，我在此确认它同时是 T2 全部下文的 first gate。

## 二、L0 构建级：全部现成，但有两个不显眼的坑

L0 六判据全映射现成 CHK（CHK03/01/09/08/05 + make exit 0），看似白给。但我读到两处仓内证据后认为要补两个判据：

**坑 1：构建可复现性必须进 L0。** 基线§四#10 caveat：48 包字节差 max 0.051%、全等 0/48，三随机源未修。若 L0 绿但产物字节漂移，M1 的差分门禁（vs factory）与一切回归比对都失真。所以 L0 新增判据：同 spec 连续 N 次构建唯一内容哈希数 =1（规划 §2.3 的确定性指标，落位在 L0 而非统计层，因为它是单次可判的）。

**坑 2：墙钟类判据的假红。** qacore README 移植留档明确记录：match3 那轮 CHK09 墙钟抖动连 oracle 自己都 fail。CHK09（load ≤ maxLoadSec）是 L0 里唯一的墙钟判据，在负载波动下会成为假红重灾区，假红消耗门禁信任。设计：临界区（如阈值 ±15%）自动重采样一次取较优值，且报告里标 `retry_taken:true`——不掩盖、但不去死。加载类指标更诚实的做法是采中位数而非单点，成本是每产物多两趟加载。

L0 的日常形态：每产物 × preview 渠道快速质检（不开 autoplay），秒级~十秒级，是开发反馈最小单元。

## 三、L1 可玩级：核心难题是「可玩」的自动判定

规划 §2.1 的 L1 有四件事，逐个想怎么落地：

### 3.1 事件流断言——先跟 spec 对齐，别想当然

第一反应是断言 `pf:ready→pf:start→pf:first-interaction→pf:end(win)` 线性时序。但 engine-bridge spec §2.2 明确写了：**pf:ready 可能先于或后于首次交互**（异步派发，不改变相位）。所以偏序断言必须是：`ready` 恰一次、`end` 恰一次（带 detail.win）、`start < end`、`first-interaction ∈ [start, end]`（无交互的 end = 自导自演，正是假可玩特征）、`end` 时刻 ≤ autoplay 预算。这提醒我：**事件流断言的依据是 engine-bridge 冻结契约，测试要引用 spec 条款号，不能凭直觉写序**——写错序的测试会把合法产物判死。

实现上现 probe 只记 ready/end/endWin 三个时间戳，需扩成全 `pf:*` 事件时间线（含 detail）。这是探针族的确定性扩展，风险低。手势数下限：autoplay facts 已有 gestures 计数，直接断言 ≥ 下限（下限按 kernel 分型，K3 实时类天然多于 K1）。

结束页可见性现在有两个来源：`__PF_QC__.endScreenVisible()` 白盒自报（可被假可玩永远 return true 骗过）+ MUT-03「结束页不可达」变异。我的主张：endScreenVisible 断言要加**档 2 交叉证据**——end 事件后画面相对 playing 末帧的像素差（结束页出现必有画面跳变），白盒与黑盒证据同时在场才计 pass。变异样本 MUT-03 恰好用来证明这个双证据判定器真的能红。

### 3.2 反假可玩双判据——统计效力与机制分型两个深坑

判据 A（随机策略胜率显著低于提示策略胜率，各 N≥5）：同一产物两批 autoplay，批 1 走 hint()，批 2 判官侧随机手势（不调 hint），统计 pf:end(win=true) 比例。这里坑很深：

- **统计效力**：N=5 的二项比较基本无显著性可言（1.0 vs 0.2 勉强，0.8 vs 0.4 完全分不出）。N≥5 是下界不是设计值；门禁实际取 N≥10，且「显著」要么用 Fisher 精确检验给 p 值，要么干脆降格为描述统计（差值 + 区间）不称「显著」——统计口径细节归 T4，但 L1 判据的实现必须留给 T4 的样本量结论以接口（N 参数化、报告落原始胜率而非只落布尔）。
- **机制分型**：K1 解谜类随机胜率趋 0，判据 A 天然好用；**K4 放置/点击类随机点也在进展，随机≈提示，判据 A 结构性失效**。这正好印证规划 §3.2「QC 契约按 kernel 分型」——L1 判据 A 也必须分型参数化：K4 把「胜率」换成「时限内目标达成率」，K3 实时类把 hint 从「必胜步」改「脚本化演示轨迹」后，对照策略是随机操作存活时长/得分。结论：**L1 反假可玩是一个按 kernel 查表的判据族，不是一条断言**，测试配置与 QC 契约三型（solver/脚本轨迹/目标达成）同源，避免两处分型漂移。
- **随机策略的登记**：随机种子、手势分布写进报告（评测输出可复跑的文化要求），否则随机批不可复现。

判据 B（CHK11 帧间动态性 + 输入响应因果性）：
- 帧间动态性：同相位 ≥6 帧连采。实现我倾向判官侧 CDP screencast 而非页内探针截图——判官侧采集天然保持档 2「探针只读、判官侧驱动」的解耦性质，且不受 canvas 跨源隔离影响。
- 但我必须指出规划这条的**残余作弊面**：背景恒动动画 + 死游戏区，帧间动态性照过。所以因果性判据我建议做成**局部因果**：手势坐标邻域窗口的前后像素差，须显著大于远端基线窗口——排除「无论点哪画面都在动」的假因果。「同坐标两种输入画面必须不同」（tap vs 拖拽过同点）现成可做，作为第二腿。
- CHK11 需要自己的变异样本（暂称 MUT-05 静态海报变异：游戏区替换为高方差静态图，恰命中帧间动态性——这正是规划 §八 点名「CHK05 单截图可被骗过」的那个攻击面的靶场；MUT-06 输入剥离变异：背景动画保留、输入处理器摘除，恰命中因果性）。

### 3.3 与 3.4：钩子义务与变异覆盖

`__PF_QC__` 产物义务：静态断言（源里含定义）+ 动态断言（hint/state 可调用），简单；关键是报告每条 L1 判定必须带 `judge_drive_tier` 字段——档 1 判据只对我方产物合法，oracle/外部输入禁钩子（规划 §八），分档统计严禁合并。

变异覆盖门禁：每个在用 CHK ≥1 恰命中样本（exit 1 且 fail 集恰为期望 CHK——现 mutations.mjs 的「恰命中」断言语义照抄）。除 MUT-03/05/06 外还要补：CHK06 的「CTA 点击但退出接口未调」变异、CHK02 的「文件数超限」zip 变异。元测试一层：变异构造算法本身 golden 化（构造产物 sha256 冻结），防变异样本悄悄失效仍绿。

## 四、L2 可投级：静态 + 运行时两层，zip 是最大改造点

L2 = 七渠道全过门。我按「不开浏览器能测多少」来分层：

**静态层**（快、可并行）：①zip 结构断言——structure 数组逐文件存在、maxFiles、ASCII 文件名、entry 名。CHK02 实装本质是「解 zip 清点」，而 qacore 收 zip 是接口级改造（run.ts:83-88 现在对 zip exit 2）：解压临时目录→伺服 entry。②外链扫描扩展到 zip 内全部文本文件（html/js/css），meta 的 forbidMraid 收窄扫描、google 的 exitapi.js 白名单例外（owner 批后）都挂在这层。③requiredMeta/config.json 三层校验（规则库声明→生成器映射→schema）。④规则库自身的元测试：evidence 完整性（无 evidence 且超龄条目 rules-check 拒绝）+ override 只许收紧的单调性断言——**规则库是被测对象的判据来源，它自己必须先有测试**，这是 D9 欠条的制度化对冲。

**运行时层**（每渠道开浏览器）：CHK06 实装=注入记录型渠道 stub。现 run.ts 的 mraid.js 桩「不定义任何全局」，要升级为定义全局并记录调用的记录型 stub（四类协议：mraid/FbPlayableAd/ExitApi/openAppStore），驱动到 CTA 后断言被调接口 + 参数=landingUrl。要点：stub 是运行时注入不进包体，请求记账里 entry.stub 字段已区分两者，这个基础直接可用。Meta CTA 双写探测（onCTAClick 优先回落 onComplete）= stub 两个都定义、断言调用序。静音逐渠道 CHK04 现成。

**渠道维度的测试算力取舍**（规划 §七：快速回归 2 渠道 preview+meta）。我发现一个问题：preview(window-open)+meta(fb-playable) 只覆盖 2/4 退出协议类，且**没有 zip 形态渠道**——CHK02/解压/结构路径在日常反馈里永远测不到，直到 release 全渠道才爆。建议快速回归改 3 渠道：preview + meta + google（exit-api 类 + zip 形态双覆盖），代价可接受。另一个砍法：L1 判据（胜率/动态性/因果性）与渠道无关，只在 preview 跑；渠道敏感的（L2 全部）才展开渠道维度——这比「砍轮次」更先该砍。

**L2 必要不充分**：本地 L2 判定输出必须携带每条数值的 evidence 元数据，thirdparty 证据的渠道在报告里标黄附「渠道数值置信度清单」。D2 官方工具回填留接口：回填结果进 channel-rules 的 evidence 字段，rules-check 按超龄拒绝——渠道漂移可检。

## 五、L3 吸引人级：锚 oracle，同 harness 是命门

L3 判据的共同结构是「与 oracle 同品类分布比对」，所以 L3 测试 = 外来运行器 + 分位基准 + 对照实验三件套。我的核心担忧一个字：**同 harness 的「同」怎么保证**。

**最大的坑：驱动策略降档。** oracle 无 `__PF_QC__`，只能档 2 策略驱动（网格扫描/扫掠）；我方产物平时用档 1 hint 驱动——hint 直接给最优坐标，t_first 天然快。若 L3 比对我方仍用档 1，区间判据系统性偏乐观，「同 harness」是假的。所以**L3 比对时我方产物必须强制降档到与 oracle 相同的档 2 策略**，报告记 judge_drive_tier=2。这一条不写死，L3 全部数字都在撒谎。

时序指标落地：t_first≤5s、t_tutorial≤4s、总时长落同品类 [P25,P75]、CTA 时机形式对齐分布、超 P90 或首屏 10s 零交互 fail（红路）、区间外偏离登记不 fail。oracle 侧阶段边界用像素活动序列估（t_cta_est:true，不当精确值）——测试实现上这是逐帧像素差序列的变化点检测，阈值要拿 6 条已下载语料先标定。

attract 剧本生效性（nearWin/failBait 实测改变胜率与时长）：这是纯 A/B 对照实验，同 spec 开/关 attract 各 N 轮，断言效应方向与幅度——不需要 oracle，可以做成集成测试早期跑，是 L3 里唯一不依赖分位基准的机检项，建议最先落。

QCTR 代理本地化：QClicks=总点击−(hasty+proximity+auto+early)，每分量判官侧 Playwright 可测（点击坐标距 CTA 边缘、距首帧时延、5 秒返回）。规划已警示空打脚本 auto 分量天然爆表——所以**必须在「人类式点击序列」下测**。人类式怎么定义？我的答案：不拍脑袋，**从 oracle 运行器采集的 pointer 时间线拟合**（反应延迟分布、位置抖动、点击间隔），即人类式策略参数本身是从 oracle 学的分布。这同时把「判官策略」也纳入可复现登记（参数 sha256 冻结）。

盲评协议（软判据、登记不设门）：混排、去标识、随机左右位、二元+三档严重度、判官 prompt/模型/参数冻结 sha256。防漂移三件套：①锚定题——判官组混入已知答案锚样本，锚题错则该轮判官作废；②双判官独立评，一致率低于阈值作废（规划 §八 已要求评分者间一致性独立测 3 次）；③针对 holdout 表现的任何 prompt 修改作废该轮重跑。VLM 不单独当门（CLIP 代理分教训，基线§3.5），只对指标已判偏离条目做。

F 轴咬合：F0 是纯数据断言（产物机制集合 ⊆ GameProfile 抽取清单且逐项有实现证据），单元级、反幻觉同源；F1 双录对比要抽象到「输入类型×响应类型×时延分布」层级——源游戏与产物坐标空间不同，逐点比对必假红；F2 与 L3 盲评共用装置。

## 六、开放问题（留给 stage4 与 T4/T5 的接口）

1. K4 放置类的判据 A 分型参数（目标达成率阈值）谁定、何时定——建议随 QC 契约三型 spec（M1）一起冻结。
2. 局部因果性判据的窗口尺寸/显著性阈值的标定数据从哪来（可能要拿 factory 48 包先跑一遍分布）。
3. N 的算力乘法：L1 双判据 2×N 轮 × 30 款 benchmark，与渠道维度怎么正交切（我倾向 L1 只跑 preview，但「渠道无关」本身需要一次全渠道验证后才敢冻结该假设）。
4. 帧间动态性在低端机型节流（4×CPU throttle）下是否假红——不可达性比对（规划 §6.3④）建议与 CHK11 共用节流环境。
5. 快速回归渠道集是否采纳我的「+google」建议，属算力与覆盖的权衡，需 owner/总架构（T1）裁定。

## 七、一句话收束

L0 靠现成 CHK 加两条新判据（可复现、墙钟容忍）；L1 的灵魂是反假可玩双判据按 kernel 分型 + 白盒/黑盒双证据 + 变异证明有效；L2 的关键工程是 zip 支持与记录型 stub，且静态层先于运行时层；L3 的命门是「同 harness 双侧同档驱动」+ 策略参数从 oracle 拟合。全部设计踩在采集-判定分离、skip≠pass、judge_drive_tier 分档这三块现有文化的地基上。
