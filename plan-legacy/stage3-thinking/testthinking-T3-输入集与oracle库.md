# 测试思考 T3：真实游戏输入集与 oracle 样本库

> 视角：输入集建设与元数据规范、oracle 库校验、版权合规流程化、版本化与冻结。
> 纪律：本文只写「怎么想」；事实与推断分栏标注；不读其他视角产物；本次实跑的命令与其输出原样引在文末「本次实跑」。

---

## 一、这类测试的特殊性：它防的不是「跑不过」，是「跑得很绿但尺子被换掉」

我这一视角管的两类资产——benchmark 输入集（≥30 款真实游戏）与 oracle 样本库（30 条三层样本）——有一个普通单测没有的性质：**它们是回归测试的常量部分**。合成层、判官层的一切数字都是相对它们而言的。这意味着它们坏掉时不会报错，只会安静地改变结论：输入集偷偷换题，L2 通过率就不再可比；oracle 库链接失效或内容被换，L3「分位数达标」就换了尺子。

这正好撞上基线里三条已付过学费的系统性缺口：

- 基线 §六.1：留档未随快照迁移，根因是 .gitignore 有意排除，约 6 处 A 级主张永久停在 B（规划 §五.1 已把「新仓第一天白名单」列为硬前提）。
- 基线 §六.6：留档写盘纪律——复跑就地覆盖 386 文件中 380 个，**复跑即毁前跑**。oracle 派生指标目录若「重算即覆盖」，等于每次跑批都在抹掉上一轮证据。
- 基线 §六.2：台账数字漂移未被机制拦截（233 vs 184、13 vs 15）。手维护的输入集/库登记册必然重演。

所以我这一层的核心主张只有一条：**凡「登记」必须机生，台账只作为机生报告的渲染层**。人写台账的那一天开始就进入漂移倒计时。

## 二、分层：把资产测试拆成五层，每层判据不同、失败含义不同

按「开发可见 / holdout」两分对资产不够用——它把「schema 缺字段」和「线上广告挂了」放进同一层，失败时不知道该找谁。更有用的分层是按**失败修复的责任人**分：

| 层 | 对象 | 判据形态 | 失败含义 | 节奏 |
|---|---|---|---|---|
| A 契约层 | 元数据 schema、必填字段、枚举白名单 | 纯静态，单次解析 | 登记表写错了，改表 | 每次提交（秒级） |
| B 自洽层 | 计数完整性、去重、覆盖矩阵、指纹冻结 | 静态扫描 + sha256 重算 | 库被改动了没走变更单 | 每次提交 |
| C 形态层 | 每条输入「可执行」——源码可构建 / URL 可采集 / 文字可解析 | 需真跑（跑构建或跑采集器） | 输入本身腐坏（站点下线、构建脚本过期） | 每日 |
| D 活性层 | oracle 源包活体可达性（HTTP/字节/语义三级） | 需出网 | 线上源变了或没了 | 日/周/月三级频率 |
| E 接入门 | 以上全部被门禁与差分 harness 消费，且自身有变异测试 | 真跑门禁 | 校验器本身是空壳 | 每门禁 |

A/B 层必须是纯 Node、无依赖的秒级单测（理由见第五节「环境即门槛」）。C 层要构建/要浏览器，天然慢。D 层要出网，是唯一天然不稳定的一层——**不稳定的一层绝不能和稳定层用同一个判据语义**，这是我下面第五节要展开的。

## 三、输入集（benchmark）的测试点

规划 §3.3 给了字段 schema（`id/source_url/fetched_at/license/type_tags(家族)/input_tier/expected_min_level/is_holdout/first_seen_at`）和活体率 ≥80% 的门。我逐条想它怎么测，以及哪里口径会塌。

### 3.1 A 层：必填与枚举

九个字段全必填，`type_tags` 必须落在 26 家族枚举内，`input_tier ∈ {T1,T2,T3,T4}`，`license ∈ {MIT,AGPL,BSD,Apache-2.0,...,proprietary-observation}`，`expected_min_level ∈ {L1,L2,L3}`，`is_holdout` 是布尔。我主张用**闭合枚举而非自由字符串**：家族名写错（`A1` 写成 `match3`）在自由文本下不会失败，只会让覆盖矩阵静默少一格。这类错误只有 schema 能挡，schema 挡不住的就归到 B 层矩阵扫描去暴露。

### 3.2 B 层：覆盖矩阵与两个「达标」口径打架

规划里有两个数：§3.3 说 benchmark 覆盖 **21/26 家族**，§七 M2 出口说「机制族 **≥10**」。这两个数不同分母，直接后果是「覆盖矩阵达标」这条判据现在**不可测**——我没法写断言，因为不知道该断言 ≥10 还是 ≥21。这是必须由合并裁定者/owner 拍的一个开放问题（我列在第八节）。我的倾向：**M0 按 21 家族登记、M2 按 ≥10 机制族判过**，但两套数都要在矩阵报告里同时列出，且每个家族标三态：`覆盖(≥1 条)` / `缺额(0 条但登记在案)` / `未登记`。只有「未登记」才是缺陷，「缺额」是路线图状态，不该让门禁红。

我还想要一条**闭包检验**的可测化：§3.1 说要把 CrazyGames 15 类 + Poki 39 类逐条映射进 26 家族。这张外部目录表以数据形式落进仓（54 行，每行 `{platform, platform_category, family_id|null}`），然后断言「family_id 为 null 的行数 = 0」。这把「分类学穷尽性」从哲学命题降级成一条计数断言——本仓已有范式：gate-m1.mjs:83-85 把「golden 1 + bad 6」数目钉死成硬断言。

### 3.3 「活体率 ≥80%」这个口径我认为是混的

三种输入形态的「活」根本不是一件事：T1 源码件的活体性 = 还能不能构建；T2 URL 件的活体性 = 站点还能不能取到（HTTP 200 且内容还是那份游戏）；T3 文字件的活体性 = 描述还能不能被解析成机制清单。把三者揉成一个「活体率 ≥80%」，分母就不自洽——源码件没有 URL，「验活」验什么？

我建议拆成三条独立判据，各自 100%/80% 分开报，且规划 §3.3 的禁令「三层成功率不得合成单一总成功率」在这里同样适用：
- T1 源码件：**可构建率 = 100%**（低于 100% 说明登记了一个跑不起来的输入，这条我没得商量）；
- T2 URL 件：**可采集率 ≥80%**，且失效条目必须显式登记 `liveness_state ∈ {ALIVE, DEAD, STALE}`，不允许靠删条目提分——这是关键：80% 的门如果允许「删掉死的就 100% 了」，那它测的不是资产质量而是删条权限。所以门禁要同时断言「活体率达标」+「条目集合未在无变更单的情况下收缩」；
- T3 文字件：**可解析率 = 100%**（外加至少一条「必须被判为坏输入」的对照件，见下）。

红路侧还要有**坏输入对照**：holdout 集要求 ≥20% 坏输入（T5 的事），但**开发可见的输入集里也必须常驻一小撮负例**——非游戏输入、畸形描述、分类学外输入。理由是仓内已有的「阴性对照」范式：qacore.test.mjs:114-139 两条 CHK10 阴性对照证明「检查不是永绿」。我的主张是：输入集里不带负例，等于 intake 层的第一版永远不会被测到拒收分支。

### 3.4 C 层：形态可执行怎么测

「可执行」不能靠人看。对每条输入，测试要断言它**真的走过它所属形态的那条链路**：
- T1 → 跑构建器，产出物存在且非空；
- T2 → 跑采集器，产出的本地副本 sha256 与登记的 `snapshot_sha256` 一致，且副本 sha256 与源站 body 一致（这两个 sha 是不同东西，别混）；
- T3 → 跑解析器，产出 GameProfile 且 `mechanisms` 非空。

三条断言各自要带**定位信息**：失败时输出必须指名条目 id + 来源 URL + 失败阶段，否则 30 条输入的批跑失败无法归因（这正是规划 §八「可诊断率」四量之一在我这层的落点）。

### 3.5 去重：同款多创意变体是合法的，精确哈希去重会误伤

规划 §6.2 引用 MM-B 的实测量：「同款游戏 2–5 个创意变体」，并据此裁定服务设计要补变体维度。这条事实直接决定了去重键的设计：**唯一性键必须是语义键 `(game_id, variant_id)`，字节 sha256 只能查「是否同一份字节」**。如果只按 sha256 去重，21 条里同一款的不同创意会被当成重复删掉，库就悄悄从「覆盖 N 款游戏」缩成「覆盖 N−k 款」而计数不变形（因为删除后仍 ≥30 也能过）。

反向还担心**过严去重**：minhash/ssdeep 之类近似去重会把同款同机制的合法变体判成重复。v1 我主张近似去重**只报不设门**，只列「疑似同源」清单供人工裁决。仓里有现成体例——gate-m1.mjs:231-234 中性名扫描「命中 >10 处时只报告不修改（改名/声明问题不碰，法务裁定）」。

## 四、oracle 样本库的测试点（含本题最难的一问：活体可达性）

### 4.1 完整性：三层构成钉死

规划 §6.2 定 30 条 = L1 官方件 10 + L2 开源产线 8 + L3 真实在投 ≥12。这个「10/8/12」应该是硬断言，不是描述。照抄 gate-m1.mjs:83-85 的数目钉死写法：解析校验器输出里的摘要行，正则抓出三个数字，与期望比对，不等即 FAIL。同理断言「M0 出口条件：30 条全部有 sha256 + fetched_at + license_status」，`license_status` 为 null 的条目数必须 = 0。

### 4.2 活体可达性复验：把「链接失效」拆成四态，这是我这一视角的核心设计

规划 §6.2 引用 MM-B 实测「2026-10-03，21/21 HTTP 200、无鉴权、0.09–1.67MB 单 HTML」。**本次我没有复验这个数字**——全仓 grep `zplay|lolipop` 零命中，21 条语料不在本机任何位置，所以下面全部是设计，不是对现况的判定。

风险在于：一天后重测，可能 20 条仍 200。**200 恰恰是最危险的状态**——因为「HTTP 200」不等于「还是那份广告」。站点换游戏、换创意、下线换成落地页、CDN 返回一个错误页 HTTP 200，都能骗过朴素的探针。我主张四态而非二态：

| 态 | 判据 | 库的动作 |
|---|---|---|
| ALIVE_UNCHANGED | 200 + body sha256 = 登记 sha256 | 无动作 |
| ALIVE_CHANGED | 200 + sha256 变了 + 运行器仍能产出结构/行为双组流 | **不算失效，但必须出变更单**：重标 fetched_at、重跑分位数、库版本 bump |
| DEAD | 4xx/5xx/DNS 失败/超时 | 条目标 `retired`，从分位数计算中剔除，**但条目记录不删** |
| GONE_BY_POLICY | 403/404 且 host 不在采集 allowlist | 视同 DEAD，留原因 |

三级证据各管一段，缺一不可：
- L1 **本地字节级**（最快）：隔离目录里源包 sha256 重算。它只证明「我手上这份没被动过」，**不证明线上还活**——所以它不能单独当活性判据。这一点我要写死，因为「本地文件在、sha 对得上」是最容易骗过自己的一种安心。
- L2 **HTTP 字节级**（日跑）：GET + content-length + content-type + body sha256，只跑 HTTP 层，不跑浏览器。便宜，是发现 ALIVE_CHANGED 的主力。
- L3 **语义级**（周/月跑）：外来广告运行器真跑一遍，产出 d4 同构流 JSON，断言「结构组 + 行为组非空」。只有它能识别「200 但已不是可玩广告」。

频率分层本身就是抗噪设计：日跑发现「变了」，周跑确认「还是不是广告」，月跑重出分位数。

### 4.3 防静默劣化：一个我认为规划漏掉的三条机制

光有探针不够，因为探针只告诉你「现在坏了」，不告诉你「在你没注意的时候已经坏过一阵又碰巧好了」。三条补机制：

1. **分位数与集合绑定**。L3 达标判据是「落在 oracle 同品类 [P25,P75]」，那么 P25/P75 就必须和产出它的**那一份集合**绑死：发布基准时记 `oracle_set_sha256`（把当次全部条目的 id+sha256 排序后取哈希）。之后任何人增删条目，分位数基准的 seal 校验就失配 → 强制重新发布。**否则会出现最难查的一种坏法：M3 发布的分位数悄悄换了尺子，M4 的「达标率 ≥60%」却还是绿的。** 我认为这是本题里最隐蔽也最致命的一条。
2. **超龄分级，不是一刀切**。`fetched_at` 超过我建议的 30 天 → 报告标 `STALE` 并进 WARN 列表；超 90 天 → 该条目**不参与分位数计算**但仍在库。理由：宁可在分位数里少一条，也不要拿一条两年前的老素材当 2026 年市场基准。规划 §6.2 已经说了「语料按采集日期分层，2019–2021 老素材无 MRAID 注入」，那分层就该有执行力，不能只是一句提醒。
3. **evidence 机制复用**。规划 §4.3 D2 给渠道规则定的 `evidence:{type,url,verifiedAt}` + 「rules-check 拒绝无 evidence 且超龄条目」——我认为这条**应当原样搬到 oracle 条目**上。同一套机制解两类漂移（渠道数值漂移 / 语料漂移），仓内还有现成实现骨架（verify-reused-assets.mjs 的登记册 + 重算 + 漂移 exit 1）。不要为 oracle 再发明一套。

### 4.4 校验器自身的测试：不给 oracle 校验器写变异测试，它就是个空壳

规划 §八 已有「变异覆盖硬门禁：无恰命中变异样本的 CHK 一律未证明有效」。同样的逻辑必须施加到**资产校验器**上。我给一组「劣化变异」：

| 变异 | 注入 | 校验器必须 |
|---|---|---|
| META-01 缺字段 | 删某条 `license` | 报出该条 id + 缺失字段，exit 1 |
| META-02 坏枚举 | `type_tags` 塞未知家族 | 报家族不在枚举，exit 1 |
| SHA-01 指纹漂移 | 改登记 sha256 一位 | 报该条 drift，exit 1 |
| DUP-01 语义重复 | 复制一条仅改 variant_id | 报 (game,variant) 冲突，exit 1 |
| LIVE-01 假活 | 某条 source_url 指向一个返回 200 的无关页面 | 语义级复验报「结构/行为组为空」，该条降级为 DEAD |
| COUNT-01 计数塌 | 删 3 条使总数 <30 | 报完整性 FAIL，exit 1 |
| STALE-01 超龄 | 把某条 fetched_at 改到两年前 | 报 STALE 并在报告中从分位数计算集剔除 |

关键断言形态照抄 qacore.test.mjs:77-99 的「恰命中」：`assert.deepEqual(failedIds, [expect])`，不允许一条坏数据同时引爆三条检查。

## 五、版权与合规怎么变成流程测试

规划 §6.5 六条红线，我逐条想「它的可测形态」：

| 红线 | 机器可测的断言 | 复用的仓内范式 |
|---|---|---|
| ①源包不入 git | 入库树（`git ls-files`）对 oracle 隔离目录零命中；全树零 `.html` 大文件 | gate-m1.mjs:167-187 `trackedFiles()` |
| ②源包不外发/不进交付包 | 打包器/交付物打包输入白名单排除 oracle 目录 | 新增，白名单化 |
| ③**源包严禁进 LLM 上下文** | **canary 测试**：往 oracle 目录放一个含唯一标记串的假源包，跑一次生成腿，断言标记串零出现在 prompt 记录、产物、日志里 | 无现成，需新造 |
| ④GPL-2.0 件不参考 | `license_status` 白名单断言 + 仓外词表扫描 | gate-m1.mjs:189-235 中性名扫描 |
| ⑤录屏/APK 提取挂起 | `license_status ∈ {allow, observe, pending_legal}`，pending 条目被任何消费者触达即 exit 1 | 新增 |
| ⑥对外只发派生特征 | 交付包内容清单断言：只有派生 JSON/缩略图，零源包 | 新增 |

③ 是最难测的一条，因为它是**流程承诺**而非文件状态。我的办法是把它降维成一个字符串事实：**canary token 不出现测试**。任何「不许把 X 送进 Y」的承诺，都可以这样变成一条可回归断言。这是本文档最想推荐给其他视角的一个通用手法。

另外两层：
- **出网约束本身要测**。活性探针和 T2 采集器都要发 HTTP 请求，必须只允许 http/https、校验 host、拒绝 localhost/环回/私有/保留地址。这条要配一组 SSRF 元数据注入测试：`file://`、`127.0.0.1`、`169.254.169.254`、`10.0.0.1`、`[::1]`、十进制 IP 变形等，断言全部被拒且给出 exit 2/1。注意仓库自己的判官在 `ArtifactServer` 上跑本地伺服（run.ts:119-126 用 127.0.0.1 + 端口白名单），如果新加的 URL 白名单写成「禁 127.0.0.1」，会把自家 harness 也打死——**规则必须区分「采集器出网」与「判官本地伺服」两条路径**。
- **合规事实的口径漂移**。21/21 无开源许可、GPL 不参考，这些是法务判断不是机检。机检只能保证「登记字段与声明一致」。所以我要一条纪律：所有合规声明以 `license_status` 字段 + 证据 URL 为准，文档正文不重复叙述，避免两处漂移。

## 六、版本化与冻结：防「中途换题」的正确姿势

我观察到一个常见误区：把「冻结」理解成「不许改」。这在实践中一定守不住——owner 改了范围，测试就名存实亡。**可执行的冻结是三件套**：

1. **版本号**：`datasetVersion` / `oracleVersion`，语义化，仅在条目增删改时 bump；
2. **内容寻址**：每条有 sha256，整库有 `set_sha256`（条目 id+sha256 排序后哈希）；
3. **锁定文件**：跑批时把 LOCK 里的版本与数据目录实况比对，不一致 → **exit 2（用法错），不是 exit 1（红）**。这个区分很重要：版本不匹配是调用姿势问题，不是质量失败；混进红灯会污染失败分类学（规划 §八 F1-F8）。

门禁怎么测「没偷偷换」：
- **台账 sha 复验**：照 verify-reused-assets.mjs 写一个 `verify-inputsets.mjs`，重算每条 sha256 与 bytes，漂移 exit 1；并入 `npm test` 与 gate（gate-m1.mjs:146-159 的门项 4 正是这个形状）。
- **变更单调剂**：条目集合变化必须产出一个 machine-readable change-set（加了哪些、删了哪些、为什么），门禁断言「set 变了但 change-set 为空」或「change-set 非空但 set 未变」→ FAIL。这条把「随手改一下」变成必须解释的动作。
- **分位数基准 seal**：`benchmark_id + oracle_set_sha256 + 提交号 + published_at` 一起冻结（对应规划 §七 M3 的「holdout seal 登记提交号+sha256」同形）。

还有一个来自 §5.3 的隐患会打到这一层：字节确定性的三随机源之一是**时间戳**。oracle 派生指标 JSON 若带易变字段（相对路径、机器名、迭代顺序），sha 天天漂移、门禁天天红，红三次就没人看了。所以：**派生指标必须可复算、无环境变量入账**——这是仓内「评测输出无时间戳可复跑」的文化，我把它写进派生 JSON 的 schema。

## 七、判据汇总（建议落成 M0 门禁条目）

```
A 层（秒级，红线）
  A1 必填字段齐全            = 100%
  A2 枚举无越界              违例 = 0
  A3 oracle 30 条三层构成    10/8/12 钉死（数目钉死范式）
  A4 sha256+fetched_at+license_status 齐备   null = 0
  B 层（秒级，红线）
  B1 每条指纹重算            drift = 0
  B2 语义去重 (game,variant) 冲突 = 0
  B3 输入集条目数 ≥30 且未在无 change-set 时收缩
  B4 分位数 seal 与 oracle_set_sha256 失配 = 0
C 层（日跑，红线）
  C1 T1 可构建率 100%；T2 可采集率 ≥80%；T3 可解析率 100%
  C2 任一形态 skip 占比 >10% → 整批不采信（规划 §二铁纪律，原样搬）
D 层（日/周/月，三态）
  D1 ALIVE_UNCHANGED ≥80%；ALIVE_CHANGED 须有 change-set
  D2 超 90 天条目不参与分位数（标 STALE，不删记录）
  D3 网络不可得 → SKIP-ENV，计入并报告；连续 N 次 SKIP-ENV 本身报警
E 层（每门禁）
  E1 元数据/活性/计数 7 类劣化变异各自恰命中 → 校验器被证明非空壳
```

关于 D3 的「连续 N 次 SKIP-ENV 本身报警」：借规划 §二的 **skip ≠ pass**。仓内现有纪律是「skip 不算过」（AGENTS.md；checks.ts 头部注释把 CHK02/06 显式标 skip 并禁止标 pass）。我加一步：**skip 要被计数、跨轮累积、超阈值报警**——否则常年断网的机器会拿到一份「全 STALE」的绿灯报告，正是基线 §五.1「台账绿、快照红」的同类病。
