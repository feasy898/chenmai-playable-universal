# T1 测试总架构 · 思考轨迹

> 视角：测试总架构（T1）。写作时间 2026-10-03。对象：`最终规划文档.md` v1.0（权威）。
> 文体：思考轨迹，不是测试文档。所有结论都是「我当前怎么想、为什么、哪里不确定」。

## 0. 起点：先想清楚测试架构在这条产线里是什么东西

拿到规划文档我的第一个反应不是「列测试用例」，而是意识到一个结构性事实：**这份规划的验收语义已经是测试语义**。DoD 是 L×F 二维判据表（规划 §2），M0–M4 每个里程碑都带量化放行条件（§七），§八直接就是测试策略纲要。所以 T1 的真正问题不是「测什么」——规划已经写得很密——而是：**这些数字和判据，由谁、在哪一层、以什么成本、以什么证据等级产出**。测试架构是产线的镜像产线：产线产 playable，测试架构产「关于 playable 的可信断言」。断言本身也要有质量纪律，否则就是用一层自说自话去验证另一层自说自话。

三个约束源在约束我的设计：

1. **基线 §六 的系统性教训**：环境即门槛（§六.3，qacore.test.mjs 现在 5/5 fail 就因为 playwright 未装）、留档断链（§六.1，.gitignore 排除 tmp/out）、台账漂移（§六.2，233 vs 184）、复跑覆盖毁前跑（§六.6）、无 git 历史。这些不是背景故事，是测试架构必须逐条咬合的「设计输入」。
2. **现有 qacore/gate 文化**：我实读了 `qacore/src/checks.ts`、`run.ts`、`tests/qacore.test.mjs`、`tests/mutations.mjs`、`scripts/gate-m3.mjs`。三态判定（pass/fail/skip，skip 严禁标 pass）、退出码 0 绿/1 红/2 用法错（run.ts:83-88 对非 HTML 直接 exit 2）、变异恰命中断言（exit 1 且 fail 集合恰等于期望 CHK）、「先清后跑、报告存在才是本次真事实」、gate-m3 的横幅对账（从子进程 stdout 正则抽数字对账，不看口号）。这套东西的成熟度很高，新仓不该重发明，该升格继承。
3. **规划自身纪律**：skip≠pass 且 skip 占比 >10% 整批不采信（§2 铁纪律二）、判官三档分档统计严禁合并（§八）、留档只追加（§5.1 硬前提）、批跑算力分层（§七纪律）。

一个贯穿全文的认识先立起来：**经典测试金字塔（大量单元→少量 E2E）的分层轴是代码粒度；这条产线的分层轴必须是「判官介入深度×失败定位半径」**。因为产线最贵的资源不是 CPU，是「一趟真实浏览器判官」（Playwright 启动+双视口+autoplay，秒到分钟级）和「一次 LLM 调用」。分层要按成本阶梯切，让开发者日常只付底层成本，统计证据只在批跑层付全价。

## 1. 金字塔怎么切：五层 + holdout 独立在金字塔外

我推翻了自己第一版按「模块」切层的想法（intake 层/understand 层……），因为那样每层都要养一整套 mock 生态，而且失败定位半径混乱。改为按判官介入深度切五层：

**L-U 单元层（无浏览器、无 LLM、无网络，毫秒级）**。对象：channel-rules 求值与 evidence 字段校验、GameProfile v2 schema 校验、失败分类器（F1–F8 判定函数是纯函数）、报告聚合与条件通过率计算、输入集元数据校验（§3.3 的 schema）、承诺覆盖表自身（见 §5）。这一层的价值是「逻辑密度最高、跑得最快」，全量预算 **<30s**。变异覆盖样本的构造与断言逻辑（MUT 系列）也在这层做单元验证——样本构造是纯文本变换，可以先离线断言「变异后字节确实变了且只变了预期位置」，再在 L-I 层验证判官命中。

**L-I 集成层（单浏览器趟或单包构建，LLM 用 mock，秒级）**。对象：packager 出包→qacore 单渠道判一闭环；每个 CHK 的金标夹具+恰命中变异样本（升格现有 qacore.test.mjs 门项 5/6 模式到全部在用 CHK）；外来广告运行器对固定语料（M0 的 6 条已下载件）端到端产出 d4 同构流 JSON 并断言 schema；三档驱动的档 2 探针注入对 mini 夹具的行为断言。预算：单件 <60s，全量 <10min。**这层是「skip≠pass」纪律的执法现场**：金标夹具上已实装 CHK 出现 skip 即整层红（现仓 QACORE_IMPLEMENTED_IDS 的做法直接搬）。

**L-E 端到端层（全管线 intake→…→report，秒到分钟级×输入数）**。这里有个我纠结最久的设计点：understand/plan 有 LLM，直接跑真 LLM 会毁掉「可复跑、无时间戳」的根基（响应方差+配额依赖）。裁定：**cassette 双模式**——录制一轮真 LLM 响应做固定夹具，E2E 默认跑 cassette 模式（确定性、可断言内容哈希），每晚定时跑真 LLM 模式（产物只登记不进差分门）。这样新线在无凭据状态下（基线教训：Higress 401、llmgw 空壳）整条 E2E 依然可跑，LLM 通道阻塞不冻结测试架构。预算：cassette 全链 30 款 benchmark×2 渠道（preview+meta 最严线，对齐规划批跑分层）约 30–60min。

**L-B 批跑层（N 轮×benchmark 全集×分层渠道）**。统计契约（§2.3 四量：条件通过率、尾部 min-over-rounds、确定性哈希唯一值数、可诊断率）**只能在这层产出**，其他层产出的是「通过/不通过」，这层产出的是「分布」。对齐规划 §七 的算力分层：快速回归 2 渠道、日跑 4 协议类代表、release 全 7 渠道×N 轮（M4 是连续 3 轮无人值守）。坑：**并行浏览器会污染时序判据**——「首含义交互 ≤5s」这类断言在 CPU 争抢下会假红。所以架构上要给「时序敏感测试」留串行槽（或空载基线对照），这个点我会明确推给 T4 细化，但架构必须预留。

**holdout 不是金字塔的塔尖，是金字塔外的另一个建筑**。它是验收协议（判官分离、物理隔离、seal、first_seen_at），不是「更大的 E2E」。把 holdout 当塔尖会导致开发者为了「跑通全塔」而触碰它——这正是要物理防的。测试架构上表现为：holdout 运行器根本不在主仓构建目标里，入口在独立凭据后端仓（规划 §八）。

失败定位半径的对应：L-U 红 → 改纯函数；L-I 红 → 定位到 CHK 编号或模板/kernel；L-E 红 → 定位到七模块之一（靠 F1–F8 的 stage 字段）；L-B 红 → 触发里程碑级回滚或承诺数字重审。每层存在的前提是它能回答「红了去哪修」，答不出就合并进下一层。

## 2. 门禁与退出码：三值退出码、四值判定态、批级元判定三级分离

现有语义（0 绿/1 红/2 用法错）必须全产线统一，这个没有争议，直接升格继承。但我发现规划把判定态扩成了四值：pass/fail/skip 之外 TIMEOUT 单列不并入 pass/fail（§八反作弊三红线之三）。所以架构上要明确：**退出码是给 shell 和门禁链看的粗分类，判定态是给报告和统计看的细分类，两者是投影关系不是同一物**。TIMEOUT 报 exit 1 但报告里必须是第三态，批跑统计里单列桶——否则「超时降级充数」就藏在 pass 里了。

「skip>10% 整批不采信」（铁纪律二）是个**批级元判定**，这里有个我在现仓文化里找到的关键先例：**这个判定不能由产出报告的进程自己下**。基线 §六.3 表扬的正是 verify_g1_reports 这类「不信任门的自报」的独立复核器。gate-m3.mjs 的横幅对账（用正则从子进程 stdout 抠出 48/0/0 再对账，不看口号）是同一精神的轻量版。所以新仓需要一个 **gate-aggregator**：只读各层留档报告 JSON、独立重算 skip 占比/条件通过率/分档统计、对账横幅数字，自己再出一份汇总报告+退出码。条件式裁定 P(L1|L0) 的分母处理也要在这层定死：分母只含 L0 通过者，**分母为 0 的桶显式标「无数据」，绝不允许静默算成 0%**——0% 会把「没测」伪装成「全挂」，是 skip≠pass 的统计版。

还有一个现仓已踩过的新坑要提前防：链式门禁里子进程超时返回 status null（gate-m3.mjs:44-45 已处理 r.error），新仓门禁链全部沿用 spawnSync+显式超时+status null 必红的处理，「子门没跑完」绝不能当「子门过了」。

## 3. 与现有 eval 文化的三个咬合点

**其一，独立复核器制度化**。每个门禁产物配一个「复核测试」：不重跑被测对象，只读留档 JSON+重算摘要断言（对应 video E10 复算偏差 0.0、peidian eval 门独立重算 spec_hash）。落点在 report-regression 模块自带 recompute 子命令。这样「报告聚合器自己错了」这件事也有检测面。

**其二，红路 fail-closed 升格为框架约定**。bad/ 目录是资产（现仓 specs-eval/bad 6 负例），每个坏输入绑定期望的 F 类和 exit 1，红路与金标同等一等公民。框架级的红线是：**判官自身崩溃、产物缺失、报告字段缺失，一律门红**——绝不允许「判官挂了但门绿」。现仓「先清后跑、报告存在才是本次运行真事实」的纪律（qacore.test.mjs 注释明言）正对着基线 §七 记录的幽灵文件事故（round1 盘点员读到并发代理的运行产物当留档），这条必须从测试局部约定升为运行器默认行为：每趟判官先删本趟目标报告路径，跑完断言存在且非空。

**其三，无时间戳可复跑——我发现了一处现仓内部口径分歧**。我 grep 验证：qacore 的 checks.ts/run.ts 完全没有 Date.now/toISOString 调用，单件报告是字节级可复算的；但 docs/diff/differential-report.json 带 generatedAt（基线 §3.1 引用「generatedAt 2026-09-30T08:29Z」）——差分层没对齐无时间戳纪律。而规划 §5.3 又把「时间戳」列为字节确定性三随机源之首。这逼我把问题想清楚：**可复跑与可追溯是两个需求，解法是内容域与封装域分离**。报告 JSON 内容字段（判定、事实、指标）零时间戳零随机序，进差分域、进内容哈希；运行时间、机器、git commit、耗时写进侧车 manifest（runs/NNNN/manifest.json），目录只追加、不进任何哈希比较。规则库 evidence 的 verifiedAt 是例外——渠道漂移检测（「无 evidence 且超龄」拒绝）本来就依赖时间，它属于领域数据不属于运行噪声，不进差分域即可。耗时类指标（loadMs）同理标为 est 类字段不进哈希——这与规划 §6.4 的 t_cta_est:true 是同一手法，「估计字段」应当成为一等公民制度。

留档制度一句话：新仓第一天 .gitignore 放行 runs/ 白名单+只追加，一切数字以实跑留档为准、报告机生非手维护（基线 §六.2 台账漂移的解毒剂）。

## 4. CI 化与本地跑：不做二选一，做三档执行环境

我先摆反方论据：基线「环境即门槛」教训（§六.3）说明这个项目群的历史失败模式恰恰是「依赖在仓外导致开箱不可跑」——7 项里 5 项如此。CI 化会放大它：CI 每次重建环境、要下载 playwright 浏览器、LLM 凭据不能进 CI（安全红线）。但纯本地也有致命伤：无 git 历史（基线局限）意味着门禁与提交脱钩，M4「无人值守批跑」又明确要求常驻环境。

裁定为三档：**(a) 本地 dev loop**——L-U+L-I+单渠道，零 LLM 凭据依赖，且**环境自检是门禁第 0 项**：缺 node_modules/playwright 时 exit 2（用法错）而非 fail，绝不让「环境缺」伪装成「代码红」——这是对基线「qacore.test.mjs 5/5 fail」事故语义层面的修复（当时 5 个 fail 其实全是环境 fail，语义上应该全绿的 0 个、exit 2 一个）。**(b) CI（若 owner 给算力）**——只跑无凭据层：L-U+L-I+cassette E2E+快速批跑。**CI 的准入条件之一是它自己能证明与本地同构**：跑一个环境指纹测试（playwright 版本、node 版本、规则库 sha256），指纹不一致降级报告。**(c) 无人值守批跑机**——真 LLM 模式、全渠道批跑、holdout 验收的运行场所，凭据不出此机。CI 是门禁触发器，批跑机是统计证据生产者，两者产物都落同一个只追加 runs/ 结构，用 manifest 里的 environment 指纹区分。

跨平台坑也要预算：本机 Windows、CI 若为 Linux，「可复跑」断言只能对跨平台不变的字节（产物 HTML、内容域 JSON）生效；报告里平台相关的路径分隔符/耗时全部隔离进封装域。否则 CI 一开，「确定性=哈希唯一值数/N」这个指标会被平台噪声打爆。

## 5. 「每个承诺至少一个测试」的覆盖性怎么检验

我粗数规划文档的规范性承诺：DoD 两表约 20 条判据、三条铁纪律、M0–M4 表约 30 条量化出口、§八约 15 条纪律——加起来 60+ 条。靠人脑记必然漏，基线 §六.2 已经证明人维护的台账必漂移。方法我设计成**机生承诺台账+双向覆盖检查**：

1. 人工首轮从规划文档抽取规范性语句，编号成 commitments.md（每条带节号、带承诺类型：门禁/登记/流程）；
2. 每条必须落到三态之一：测试 ID 或门禁项 ID（覆盖）／「不可测、降级为登记」的显式豁免（带理由，owner 签）／blocked-on-milestone（如盲评在 M3 前只有占位）；
3. 覆盖检查本身机检：CI 断言 commitments.md 无 UNCOVERED 条目；
4. **防漂移**：规划文档 sha256 写进测试 manifest，文档一变覆盖表强制重审——这正是 peidian spec_hash 漂移导致 182/184 FAIL 的教训正向复用（他们因没这机制而记账回归，我们因有这机制而强制同步）；
5. 反向检查：无承诺出处的主测试=私设判据，同样要登记，防止测试体系长出规划没认账的私货判据。

诚实边界：M2/M3 承诺（LLM 腿、盲评、oracle 分位）现在只能给占位测试与协议设计，覆盖表必须如实标 blocked，不许拿「设计文档存在」冒充「测试存在」——那是 B 级台账的老路。

## 6. 开放问题（我不装作已解决）

- autoplay 45s vs durationBudget 30s 未裁决（M0 拍板项），L1/L3 时序断言阈值现在只能写占位参数，裁决后一次性替换——测试代码要把这类「待拍板阈值」集中成显式常量表，不许散落硬编码。
- 尾部 min-over-rounds 对环境噪声极敏感，串行槽和空载基线怎么设计我留给了 T4，但架构已预留。
- holdout 判官环境是否也要 freeze（同 playwright 版本/同机器）？否则判官解耦做到了、判官环境漂移成了新方差源——规划只冻结了 prompt/模型/参数的 sha256，运行时环境没提。
- gate-aggregator 自己谁来复核（无限回归）：务实答案是它保持足够小、断言逻辑有单元测试、输出只追加可人工抽验——不追求哲学上的终点。
- CI 算力 owner 未拍板（开放问题②相关），三档环境里 (b) 档现在是假设性存在，测试架构按「CI 可缺席」设计：没有 CI 时本地脚本等价产出同一 runs/ 结构。

## 7. 一句话收束

我对 T1 的最终立场：**分层按判官介入深度切、退出码按三值统一而判定态四值、批级判定只能由独立 aggregator 下、时间戳隔离在封装域、holdout 在金字塔外、承诺覆盖双向机检、环境自检 exit 2 不冒充代码红**。这七条里每一条都不是新发明，全部是对现仓文化（qacore 三态、gate 横幅对账、先清后跑）与基线教训（留档断链、台账漂移、环境即门槛、幽灵文件）的正向继承——测试架构的原创性应该花在 cassette 双模式和承诺台账这种新问题上，而不是重造已被验证的轮子。
