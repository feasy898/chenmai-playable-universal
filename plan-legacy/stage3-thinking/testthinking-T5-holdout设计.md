## 一、holdout 的失效模式不是"不够多"，是"被看见过"

holdout 退化的原因不是样本不够，而是三件事同时发生：抽样式建集（抽样规则与数据集在同一个开发者手里）、隔离靠约定（大家答应不看）、判官自报（跑判官的和改判据的是同一个）。任何一件破了，样本量再大都只是"回归测试穿新马甲"。

仓内两处硬证据支持这个判断：

- **peidian 的 holdout 实例确实不在仓内**。`factory/peidian-agent/README-upstream.md:25` 写明验收用独立 HOLDOUT 集（15 场景 + PARK-002 独立实例）"**不在本仓库内**，由验收人持有"；我 `ls peidian-agent/HOLDOUT.md` 确认快照中无此文件（基线§5.3 亦把"peidian holdout 隔离实例"列为 D 级物理等待）。这就是物理隔离的可核对形态：不是文档承诺，是文件真的不在。
- **可玩广告两仓对 holdout 零概念**。我在 `chenmai-playable-factory` 与 `chenmai-playable-ads` 全树 grep `holdout`（ts/mjs/json/md）**零命中**。规划§八的"物理隔离 + seal 登记"目前是 0 实现起点。

【推断】所以本次重心不该放在"抽多少条"，而在**三个可机器核对的凭证**：①集合指纹（每条 sha256 + 集合版本号）；②判官指纹（判官代码 + prompt + 模型 + 参数 sha256）；③隔离自检门（开发仓对 holdout 特征串零命中，exit 1）。三者齐了才有"不可被悄悄改过"的性质；缺任一项，它只是一次普通批跑。

## 二、holdout 集怎么建

### 2.1 三层分账

peidian 是两层（`golden/dev/` 与验收人手里的 holdout）【实】。我加第三层，因为 benchmark（≥30 款）与 holdout 的**建设期**必须分开：**dev 集**（可见，日常回归与变异构造）；**seal 集**（分布公开、条目不可见——可问"A5 家族条件通过率多少"，不可问"验收用的是哪三款"）；**private 集**（验收人持有，条目本体）。

公开分布而不公开条目是唯一折中，但**反推风险真实存在**（26 家族小样本时分布≈清单）。故 holdout 的族覆盖必须显著宽于 dev 集——若它只是 dev 的子集抽样，公布分布等于公布清单。

### 2.2 抽样纪律：抽样器与数据集分离

【推断】抽样必须在 seal 之后由验收侧执行。抽样规则本身会泄漏：若"每族抽 2 款、优先高信息量"，开发者知道后会在 dev 里刻意多备同类游戏，把 holdout 分布猜出来。**规则只约束"族覆盖与形态配额"，不约束"哪一款"**。

按 **(超类 × 输入形态 T1/T3) 分层**：族级下限 1、超类级下限 4、坏输入 ≥20%（规划§七 M3 已写"≥30 条含 ≥20% 坏输入"；我倾向抬到规划§九 owner 拍板项⑪的 ≥60 条，理由见 §六算力）。C/E 两超类 v1 覆盖不全，要么标注"本轮不可达、留待 v1.5"，要么不放进本轮——**放一个已知做不了的族进去只稀释分母**。

### 2.3 元数据与冻结：复用仓内两个脚手架

规划§3.3 定的元数据字段（`id/source_url/fetched_at/license/type_tags/input_tier/expected_min_level/is_holdout/first_seen_at`）**在现仓完全不存在**——`packages/spec/playable-spec.schema.json` 顶层只有 `specVersion, meta, game, flow, assets, i18n, channels, variants, qc`【实，node 解析输出】，grep `first_seen_at|fetched_at|license` 零命中。故这是新表，不往 spec 加字段（spec 是冻结物，AGENTS.md 禁改）。

冻结机制建议**照抄 peidian 既有实现**，不另发明：①集合版本号 = 条目名+sha256 排序串的 sha256 前 16 位（`golden_set.py:248-253` 的 `golden_set_version()` 已这么干），比手写版本号抗漂移且第三方可复算；②sha256 漂移即 exit 1 的重算器——factory 已有同体例成熟件 `scripts/verify-reused-assets.mjs`（从 `REUSED-ASSETS.md` 机器可读登记册重算 sha256 与字节数，漂移即失败）【实】。

`first_seen_at` 最易沦为装饰字段，必须绑到机器可判的泄漏探测（§五.3）。

## 三、物理/流程隔离

| 层 | 机制 | 失败后果 | 先例 |
|---|---|---|---|
| L1 路径 | holdout 在仓外；新仓首日 .gitignore 白名单 + 只追加写盘 | 快照迁移丢证据、复跑覆盖毁前跑 | 基线§六.1/§六.6 两次事故 |
| L2 凭据 | owner 或独立机器持有；开发机只有"提交产物→取回报告"入口 | 本地有全集，可反复试探 | peidian README-upstream.md:25【实】 |
| L3 流程 | 解封需 owner 动作；每轮 seal 登记提交号 + 清单 sha256 + 判官 sha256 + 环境指纹 | 无法追溯跑的是哪套判官、哪批题 | 规划§七 M3 |

L1 要抄 factory 自己吃的教训：现 `.gitignore` 排除 `node_modules/ artifacts/ tmp/ *.log`【实】，而矩阵产物默认落 `artifacts/matrix`、差分证据落 `tmp/diff/`【实，两脚本头注释】——**holdout 跑批证据天然会被 .gitignore 吃掉**，这正是基线§四#10 "ledger 引用的 18 条 tmp/diff/*.json 证据悬空"的成因。留档必须建仓首日白名单放行，不能事后 force-add（基线§六.1："留档转正靠逐案手工 force-add，不是制度"）。

### 隔离自检门（照抄 peidian 体例）

我**实跑**了它的模板：`cd factory/peidian-agent && python scripts/ci_isolation.py` → `ISOLATION OK: pattern='PARK-002|TARIFF-2026B|OP-1[0-9]' zero hits in golden, scenarios, src, tests, ontology, regulations, tools, skills, prompts, assets`，`EXIT=0`。

四个值得抄的设计点【实，源码 1-113 行】：①正则外置显式列出，命中报 `file:line: matched=`，不只报计数；②**扫描目录用白名单且排除 specs/**——因为 spec 里写隔离条款自述会假红（`ASSET-MANIFEST.md:187` 登记过"specs-v2 树命中 7 行，全为隔离条款自述……真隔离面完好，非泄漏"）。**我们的移植版必须排除声明性文档树，否则门禁第一周就假红然后被人关掉**；③全部文件按文本读不按后缀过滤（`_TEXT_SUFFIXES` 注释明说仅作文档说明）——holdout 特征串可能藏在 png 元数据与 mjs 字符串里；④退出码复用 0/1 语义，不新造。

我们的特征串 = 样本 id、来源 URL、seed、文案集合、素材 sha256、URL 四元组。**我要加一条 peidian 没有的反向扫描**：不只是"开发仓不得出现 holdout 字样"，还要"开发仓产物不得携带 holdout 指纹"——照抄一个已见过的 holdout 产物，与读过 holdout 是同一种作弊，而前者不留字符串证据。

## 四、判官独立性协议

### 4.1 靠"档位绑定"，不靠"约定不看"

规划§八已定三档驱动。我补一条最易被绕过的缝：**档位不能由被测方或运行方选，必须由输入来源硬绑定**。我方产物→档1；外部输入/oracle/holdout 输入→档2 或档3，无例外。

现实证据是 `checks.ts:190-192`：CHK07 在页面无 `__PF_QC__` 时判 **fail**。这意味着**给 holdout 第三方游戏注入 `__PF_QC__` 钩子，判官会全绿**——而真实广告根本没这个钩子。所以档位绑定必须**在代码层拒绝**（外部输入路径上注入钩子的调用直接抛错），不能写在文档里。

### 4.2 判官冻结：判官也要有 sha256 登记册

判官当前还没有 prompt/模型层，但已有更值钱的冻结先例：qacore 报告字段签名是冻结物（`docs/specs/pipeline-contract.md:98`"现状全字段，冻结"），对 oracle 的字节一致性由 `npm run verify:assets` 担保【实】。

判官指纹建议登记四组，缺一不可：**判定层**（`checks.ts`+`run.ts`+`autoplay.ts`+**`probe.ts`**——探针改动会改判定结果，却不在任何冻结清单里；`qacore-amendments.md` 记载 2026-09-30 就改过探针且"逐字节一致性证据自此失效"，缝是真实存在的）；**规则层**（`channel-rules.json`，规划§4.3 加 evidence 后随之变；现**无 evidence 字段**【实，grep 零命中】）；**阈值层**（`invariants.ts:52` 的 `MAX_DURATION_SEC = 30`）；**环境**（Node ≥22，本机 v22.23.2【实】、chromium-1243、playwright 1.63.0）。

**未冻结等于允许中途改判据**。seal 文件缺这四组指纹，那一轮结论不采信——不是扣分，是作废。

### 4.3 报告必须可被第三方复算

`chenmai-feeding-arm/scripts/verify_g1_reports.py` 是仓内最佳先例，它把"独立"定义得极干净【实，行 5-17】：**只用标准库、不 import 任何被审模块、不读被审源码**——比"另写人再看一遍"强，因为可重复。

但现 qacore 报告**做不到**：`run.ts:377` 把 `server.url_for(...)` 写进报告，而服务默认 `--port 0`（`cli.mjs` 头 + `server.ts:60,70`）端口是系统临时分配的，**每次跑 URL 都不同**；`assemble-report.mjs:169` 还写了 `generatedAt: new Date().toISOString()`【实】。

建议报告**分两层**：`verdict_body`（判定体，不含环境相关值）与 `run_meta`（时间/端口/墙钟）。**sha256 只覆盖 verdict_body**。端口在判定体里退化为"已请求=0"，实际端口只入 meta。

### 4.4 开发者能看到什么

【推断】设计主张：可见——分桶条件通过率、尾部、方差、失败分类 F1-F8 计数、判官四组指纹、变异覆盖率、错误拒绝条数；不可见——逐样本判定明细、失败样本身份与产物、holdout 特征串与清单分项 sha256、变异样本本体、错误接受的具体样本（只给总数与族分布）。

**错误拒绝可见、错误接受不可见**是刻意不对称：误杀是开发者要修的，必须能定位；错误接受是红线，定位权留给验收人。

## 五、反作弊机检

### 5.1 假可玩：现判官有一个仓内可证的缺口

我把规划§八说的"CHK05 单截图可骗过"在现仓**坐实了**：

- CHK05 的判定输入是**每视口一张截图的灰度方差**（`checks.ts:153-183` 读 `facts.viewport_shots[*].variance`，阈值 `VARIANCE_THRESHOLD = 30.0` 见 `run.ts:42`，方差实现见 `pngvar.ts:223-236`），`run.ts:308` 每趟只 `page.screenshot()` **一次**。
- 金标夹具 `qacore/tests/fixtures/mini.html` 是**静态画布**：全文 61 行 2220 字节，canvas 只在加载时画一次矩形/圆/文字【实，读全文】；grep `requestAnimationFrame|setInterval|update(` **命中 0**；grep 输入事件绑定**只命中 PF 桩自己 dispatch 的 pf:first-interaction / pf:end**（行 47-56），**没有任何输入事件绑到画布重绘**。
- 它**照样过金标层**（`qacore.test.mjs:52-75` 断言 exit 0、零 fail、已实装项零 skip）【实，读断言；因缺 playwright 未能实跑，见 §八.7】。

**仓里现成躺着一个"静态帧冒充可玩"的样本，而且它是金标。** 这是 CHK11 必须先落地、且必须把 mini.html 从金标降级为"CHK11 变异样本"的最硬证据。规划§八点了 MUT-03"结束页不可达"是假可玩家族缺失的那个变异——我补一条：**MUT-03 之前应先有 MUT-00「静态帧冒充」**，前者假设游戏在跑只是走不到底，后者是根本没在跑，是更基础的攻击面。

CHK11 三条判据中，**"同坐标两种输入画面必须不同"最不可省**：前两条可被预录循环动画骗过（同相位 6 帧内画面在动），只有它能区分真响应与播放。代价是判官要在同坐标构造两种手势——`autoplay.ts:17-22` 的 `SWEEP_VECTORS` 已有基础（tap 兜底 + 定向拖拽），但需新增"同坐标双输入"探针动作。

### 5.2 判官自身先过变异测试

peidian 的 `scripts/mutation_test.py` 体例可直接移植【实，行 1-40、63-66】：变异 = 对判定层精确子串替换（限 oracle 路径白名单），跑 eval 看退出码，**非 0 = killed**；每步强制 `git checkout` 还原 + **行尾归一化后 sha256 校验**（注释明说 autocrlf 下 checkout 可能把 LF 改写 CRLF，字节级比对会误报——Windows 必踩）；脏树 → `skipped_dirty`，find 次数不对 → `invalid`；结果顶层键固定 `RESULT_KEYS`。

**必须点名一次真实事故**：`.mutations/plan-m6-notes.md:22-24` 记 `m6-holdout-addcase-allow` 存活——`add_golden_case` 的 holdout 拒绝被破坏后 **eval 仍全绿**，靠补一条负例用例（EVAL-M6-02-N2）才杀掉【实，读该文件 §2-§4】。

对我们的直接含义：**"holdout 隔离门"本身也是需要变异测试守护的判据**。变异清单必须有：①取消隔离扫描的目录白名单；②把 `is_holdout` 短路为恒 false；③把 bad 输入的 reject 分支改为放行。**没有这三条，隔离门就是永绿的装饰**。这正是任务书"变异用例里必须有模拟假可玩的样本"的要求的延伸——我认为"模拟假可玩"只是其中一支，同伴还有"模拟隔离失效"与"模拟超时充数"。

### 5.3 幻觉功能与超时降级

**幻觉功能**：`|产物机制 \ 输入抽取清单| == 0` 且逐项有实现证据（规划§2.2 F0）。我倾向**不设门，设"疑似清单"**：出现差集即登记 F6 并要求人工判读——误报成本高于漏报，这与"错误拒绝只报不设门"同源。

**超时降级**：`checks.ts` 状态只有 `pass|fail|skip`【实，行 24-30】，**无 TIMEOUT 第三态**；且 `checks.ts:194-201` 把"pf:end 超预算"并进 CHK07 的 fail 列表。于是"太慢"与"走不到底"**混在同一个 fail 里**，放行判据无法分开统计。建议报告层加第三态，聚合层把 (成功/失败/超时) 分三桶各报比率，超时率单列。理由：超时充数的典型形态正是"卡到超时后返回静态结束页"——当前语义下它被记成 fail，看起来"很严格"，实际恰恰掩盖了"根本玩不完"。

### 5.4 first_seen_at 绑定的泄漏探测

【推断】绑法：对每条 holdout 算静态指纹（seed / 素材 sha256 / 文案集合 / URL 四元组；产物侧加包 sha256 与机制集合签名），对**每条开发侧产物**做同族扫描。命中且 `first_seen_at` 早于本轮 seal → 该条目视为已泄漏 → 按规划§八**整轮作废**。补一条纪律：**已泄漏样本永久退役**，不再进任何后续 holdout——泄露过就不可信，复用会让"holdout 从未泄漏"这个统计前提悄悄失效。

## 六、验收判据与放行条件

| 档 | 判据 | 口径 |
|---|---|---|
| 一票否决 | 错误接受 = 0 | 坏输入被当合格产物放行（规划§七 M4/§八） |
| 一票否决 | 判官四组指纹已登记且运行期未变 | seal 文件逐项比对（§四.2） |
| 一票否决 | 隔离自检门 zero hits | exit 0（§三） |
| 一票否决 | 变异覆盖：每个在用 CHK ≥1 恰命中样本 | 缺则该 CHK 不计入 L1（规划§八） |
| 分层下界 | T1 桶 L2 ≥95%；T3 桶 L1 ≥70% 且 L2 ≥30% | 尾部 = min over rounds（规划§2.3/§七 M4） |
| 登记不设门 | 错误拒绝条数 | 设门会诱发坏输入构成失真（规划§八） |
| 整批不采信 | 任一级 skip 占比 >10% | skip ≠ pass（规划§二） |

**N 与口径声明**：规划§八定 N≥5 且明说"尾部形状非置信区间，报点估计需声明"。我主张报告表头**必须带一行口径声明**（"以下为 N=5 的点估计，非置信区间"），否则下游必当区间用——这是台账漂移类事故（基线§六.2）的同类风险。

**算力要用现网数据推**：`e2e-matrix.mjs:19` 实测注释记"48 包 921.8s ≤1200s 全绿（--jobs 2）"【实】。据此单格 ≈19s：60 样本 ×5 轮 ×单渠道 ≈95 分钟；×4 协议类代表渠道 ≈6.3 小时；7 渠道 ≈11 小时。**这意味着 holdout 验收不能塞进日常 CI**，必须是 owner 在场的低频事件（与 M4"连续 3 轮无人值守批跑"是两类事）。算力不可承受时**砍渠道、保轮次**——砍轮次会把"尾部"这个唯一对外承诺量毁掉。

**分片规则**：若超预算，按族分片、每片独立 seal 独立判定，**禁止拼成"总通过率"**。理由是规划§3.3 已立"三层成功率不得合成单一总成功率"，同一错误在验收层重犯代价更大（分母被悄悄换掉）。

## 七、轮换与泄密处置

**轮换应是事件驱动**而非周期驱动：分类学修订（§3.1 的 NEW 逃逸口触发）、承诺级别变更、判据口径变更（D2 门把渠道数值升为 official）。周期驱动会诱使团队把轮换当例行公事。轮换的统计代价必须写明：**新旧两轮不可合并**（分布与判据可能不同），对外只承诺当轮尾部。

**泄密处置四级**：①**冻结该轮**——不修补、不重跑、不"就这一次"；②溯源（`first_seen_at` + 指纹扫描定位是代码引用、文档引用还是产物照抄）；③清场 + 隔离门复跑 exit 0；④登记只追加台账（sha256 锚定）+ 该样本永久退役。

第①级的必要性：最大的一次自欺是"我们已经知道答案了，那就当这轮没跑过、补跑一次"。补跑结果**不是 holdout 结果，是带污染记忆的回归结果**——开发者已针对这批题改过代码。这区别须由流程强制，不能靠自觉。

## 九、开放问题（需 owner 或他人拍板，我不越界裁定）

1. **判官跑在谁的机器上、谁写汇总**？若验收人既跑判官又写汇总，"判官解耦"只在"开发不看报告"这层成立，汇总口径无人独立复核。是否需要第二个只复算不裁决的角色（feeding-arm 的 verify_g1_reports 体例）？
2. **holdout 规模与算力**（规划§九⑪）：按现网推算 ≥60×5×4 渠道 ≈6.3 小时，单次不可承受则砍渠道。是否接受？若不接受，最小可辩护规模是多少？
3. **坏输入 ≥20% 的构成失真**：错误拒绝不设门是对的（否则诱导团队把坏输入做得"刚刚好好被拒"），但 20% 坏输入同时是对拒收能力的压力测试。坏输入要不要分层（畸形描述/空输入/非游戏输入/分类学外/T5 APK）并分别报率？
4. **判官"不许改"与工程现实的冲突**：规划§八说"针对 holdout 表现的任何 prompt 修改作废该轮重跑"。但跑批必然暴露判官 bug，那时改判官是正确动作。我倾向：**允许改，但该轮作废且改后重跑全轮**——惩罚的是隐瞒不是修改。需 owner 明确表态，否则执行时会退化成"改了不声张"。
5. **holdout 与 oracle 语料的关系**：规划§六.2 的 21 条真实在投语料是公开可下载的"对齐对象"，§八说外部输入严禁注入白盒钩子。那 oracle 语料**能不能进 holdout**？我认为不能（无需隔离），但需显式写死，否则会有人拿它充 holdout 条目数。
6. **轮换触发条件的裁决权**：§七的事件驱动清单需 owner 认，否则退回"季度轮换"。
